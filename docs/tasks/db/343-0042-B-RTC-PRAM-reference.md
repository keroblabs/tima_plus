# Apple 343-0042-B — Macintosh Plus RTC / PRAM interface reference

**Document type:** Engineering component reference (not a task or bug ticket)  
**Target:** Macintosh Plus M0001AP, 6522 VIA-connected serial real-time clock  
**Component:** Apple 343-0042-B / 343S0042 RTC family, 32-bit seconds counter and 256 bytes of battery-backed parameter RAM  
**Date:** 19 November 2026  
**Related ticket:** [PLUS-EMU-0009 — Implement Macintosh Plus serial RTC and battery-backed PRAM](PLUS-EMU-0009.md)

> **Scope and evidence:** This is an original, implementation-oriented summary of observable component behaviour, not a reproduction of an Apple data sheet. The VIA wiring, 4-byte seconds counter, 1 Hz interrupt and 256-byte PRAM follow Apple's published Macintosh family hardware guide. The command-byte decoding and edge cases are cross-checked against independent MAME, QEMU, Linux/m68k and Macintosh Plus ROM implementations. Where those implementations differ, this document identifies the uncertainty rather than claiming an undocumented IC guarantee. See [References](#12-references-and-verification-status).

## 1. Which chip belongs in the Macintosh Plus?

The Macintosh Plus (including M0001AP) uses an Apple serial RTC/PRAM IC in the **343-0042-B / 343S0042** family. It is a distinct device from the MC68000 and the 6522 VIA; the Mac reaches it only through VIA Port B serial pins. The chip provides:

| Resource | Behaviour / size |
| --- | --- |
| Time counter | 4 independently addressable 8-bit bytes representing a 32-bit unsigned seconds count |
| Epoch | 00:00:00 on 1 January 1904 (classic Macintosh epoch) |
| Tick | Counter increments once per second; the one-second signal is also visible as a VIA interrupt source |
| Battery-backed parameter RAM | **256 bytes**, logical offsets `0x00`–`0xFF` |
| Legacy access | A one-byte command selects seconds registers or one of the first 20 PRAM bytes |
| Extended access | A two-byte command selects any of the 256 PRAM bytes |
| Write protection | A control register whose data bit 7 protects or permits writes |
| Serial interface | Chip enable, serial clock and bidirectional data via 6522 VIA Port B |

**Do not substitute the Apple 343-0040:** that older variant has only **20 PRAM bytes** and lacks 256-byte extended PRAM access. The Macintosh Portable also uses a different RTC arrangement (Power Manager) and is **not** the target.

The Apple guide establishes the Plus' 256 bytes; MAME labels its emulated 256-byte model `RTC3430042`. Exact suffixes/markings can vary in preservation material: for an emulator, the **Plus-compatible 256-byte protocol**, rather than the printing on a particular board, is the contractual identity.

## 2. Connection to the 6522 VIA

There is **no separately addressable RTC register bank in the MC68000 memory map**. All chip commands are bit-banged through Port B.

| VIA Port B bit | Mask | Software signal | VIA direction during normal operation | IC meaning |
| --- | --- | --- | --- | --- |
| PB2 | `0x04` | `rtcEnb` | Output | **Active low**: 0 selects RTC; 1 deselects and ends/aborts serial transaction |
| PB1 | `0x02` | `rtcClk` | Output | Serial clock generated by Macintosh |
| PB0 | `0x01` | `rtcData` | Output for command/write; input for read response | Serial data, bidirectional |

The remaining Port B pins are **not** RTC signals: PB3 is mouse button, PB4/PB5 are mouse quadrature, PB6 is horizontal/video blanking state, PB7 controls sound. The RTC integration must preserve them.

### Guest-visible VIA registers

The existing uMac VIA decoding selects a register via `(address >> 9) & 0x0F`. These are the pertinent *canonical example* Macintosh Plus byte addresses and offsets:

| VIA register | Register selector | Canonical address | Relevant use |
| --- | --- | --- | --- |
| ORB/IRB, Port B | `0` | `0xEFE1FE` | Drive PB2/PB1 and output PB0; sample input PB0 |
| DDRB | `2` | `0xEFE5FE` | Bit 0 is **1 = output**, **0 = input**; PB1/PB2 should remain outputs |
| IFR | `13` | `0xEFFBFE` | **Bit 0 = one-second**; **bit 1 = vertical blanking** |
| IER | `14` | `0xEFFDFE` | **Bit 0** enables the one-second interrupt; write `0x81` to enable or `0x01` to disable without changing other enables |

The addresses above are VIA registers, **not** addresses of the RTC time/PRAM bytes. Those are reached only by serial commands. In the 6522, a Port B read combines output-latch values for DDR=1 pins with external pin values for DDR=0 pins; the RTC must not override the host's driven PB0 when it is configured as output.

**Implementation caveat in this repository:** `devel/umac/src/via.c` currently invokes `rb_change` **before** saving a newly written ORB value and does **not** notify `rb_change` on a DDRB-only write. An RTC device needs the newly resolved PB0/PB1/PB2 pin state **and** DDRB changes; do not assume the existing callbacks already provide that.

## 3. Serial transfers

All bytes are transferred **most significant bit first**. The host always controls `rtcClk`:

```text
PB2 rtcEnb:   high (idle) -> LOW (selected) ----------------> high (done)
PB1 rtcClk:   host-generated pulses, one per serial bit
PB0 rtcData:  command bits -> [optional extended-address byte]
               -> guest data bits (write) OR RTC data bits (read)
```

A regular read is **one 8-bit command + one 8-bit response**. A regular write is **one 8-bit command + one 8-bit value**. Extended PRAM reads/writes use **two command/address bytes**, followed by one response/value byte:

| Transaction | Command phase | Data phase |
| --- | --- | --- |
| Regular read | 8 command bits | 8 RTC-to-Mac bits |
| Regular write | 8 command bits | 8 Mac-to-RTC bits |
| Extended PRAM read | 8-bit prefix + 8-bit address argument | 8 RTC-to-Mac bits |
| Extended PRAM write | 8-bit prefix + 8-bit address argument | 8 Mac-to-RTC bits |

Protocol obligations:
1. Assert PB2 low, initialize the bit counter and serial state.
2. Set PB0 as VIA output, send the command MSB-first with eight PB1 pulses.
3. For extended PRAM, transmit the second command byte while PB0 is still output.
4. For a read, switch DDRB bit 0 to **input**, then clock and sample eight response bits; for a write, keep it output and transmit the eight value bits.
5. Deassert PB2 high. A premature deselect discards the incomplete command; the next select begins a new command.
6. Preserve non-RTC Port B outputs and the rest of DDRB throughout.

**Sampling-edge cross-check:** MAME's serial RTC shifts on **clock falling edges** and makes read output valid after the fall. The inspected QEMU VIA model collects guest writes on rising edges and updates guest read bits on falling edges.

**Plus V3 ROM in uMac:** The ROM changes PB0 to input while PB1 is high, drives PB1 low then high, and reads PB0. The RTC drives response bit 7 on the first falling edge and bits 6 through 0 on the next seven falling edges. [ROM trace and regression evidence](PLUS-EMU-0009.md#verification-evidence-for-the-clock-correction-19-november-2026)

## 4. One-byte command format (register and first 20 PRAM bytes)

For the ordinary commands, use the canonical encoding:

```text
bit:    7       6 5 4 3 2       1 0
        R       A4 A3 A2 A1 A0  0 1

R = 1 read, R = 0 write
index = (command >> 2) & 0x1F
canonical command = (R << 7) | (index << 2) | 0x01
```

**Important:** The two low-order bits are conventionally `01`, **not `10`**. The extended family (section 5) is the exception and is decoded differently. Some existing emulators tolerate noncanonical low bits; do not assume all such patterns are valid silicon commands without verification.

### RTC internal register selection table

| Index `A4..A0` | Regular write command | Regular read command | Device operation |
| --- | --- | --- | --- |
| `0x00` | `0x01` | `0x81` | Seconds counter byte 0 (least significant, bits 7:0) |
| `0x01` | `0x05` | `0x85` | Seconds byte 1 (bits 15:8) |
| `0x02` | `0x09` | `0x89` | Seconds byte 2 (bits 23:16) |
| `0x03` | `0x0D` | `0x8D` | Seconds byte 3 (most significant, bits 31:24) |
| `0x04..0x07` | `0x11..0x1D` (step 4) | `0x91..0x9D` (step 4) | Aliases of seconds bytes 0..3 |
| `0x08..0x0B` | `0x21..0x2D` (step 4) | `0xA1..0xAD` (step 4) | Logical PRAM `0x10..0x13` (four bytes) |
| `0x0C` | `0x31` | Not a defined normal read | Test register; diagnostic mode, not standard time-setting |
| `0x0D` | `0x35` | Not a defined normal read | Write-protection control |
| `0x0E..0x0F` | Extended family (see below) | Extended family (see below) | Two-byte command designator, not normal PRAM register |
| `0x10..0x1F` | `0x41..0x7D` (step 4) | `0xC1..0xFD` (step 4) | Logical PRAM `0x00..0x0F` (sixteen bytes) |

The **legacy-accessible 20 bytes** are therefore **logical PRAM offsets `0x00..0x13`**. They are **not** a physically separate 20-byte array or the indices `0x08..0x0B` plus `0x10..0x1F` in the backing file. The register *selector* is not the *PRAM offset*.

**Concrete ROM-related examples:**
- `0x81` reads **seconds byte 0**, not `0xC1`.
- `0xC1` reads **PRAM offset `0x00`**. The published Plus ROM disassembly issues this command during startup and compares the returned byte with `0xA8`, a software-level initialization/signature expectation; do **not** initialize every fresh PRAM to `0xA8` as an undocumented hardware default.
- `0xA1` reads **PRAM offset `0x10`**; the Plus ROM uses that byte in its speaker-volume startup path.
- `0x35` followed by a data byte changes write protection. The conventional model uses **data bit 7 = 1 to protect**, **0 to allow writes**. Example: `0x35 0x80` protects; `0x35 0x00` unprotects. Linux/m68k uses `0x55` and `0xD5` as example values with the same bit-7 effect. Only the write-protection control itself may be written while protected.
- `0x31` is the test-mode register: raw diagnostic-clock acceleration/reset behaviour is not adequately specified for this project's normal emulation scope. Document any deliberate unimplemented test-mode subfunctions rather than interpreting `0x31` as PRAM.

The normal write-protection guard should also apply to **extended PRAM writes**. Some open-source emulators differ in their treatment of this case; use the hardware contract and guest-visible tests rather than inheriting an implementation omission.

## 5. Extended PRAM commands (all 256 bytes)

The 343-0042-B divides PRAM into **8 sectors of 32 bytes**. Given logical PRAM address `A`, an unsigned 8-bit value:

```c
// Pseudocode; read/write selection is in bit 7 of prefix.
uint8_t prefix = (read ? 0xB8 : 0x38) | ((A >> 5) & 0x07);
uint8_t arg    = ((A & 0x1F) << 2) | 0x01;

// The RTC reconstructs:
uint8_t address = ((prefix & 0x07) << 5) | ((arg >> 2) & 0x1F);
```

**Wire order:** `prefix`, `arg`, then the RTC-provided read byte or Mac-provided write byte. The second byte's bits **6..2** hold the offset within a 32-byte sector; in canonical use, bits 1..0 are `01`. Bits 2..0 of the first byte identify the sector. This is **not** a 16-bit linear register address.

| PRAM sector | Prefix (write / read) | PRAM addresses |
| --- | --- | --- |
| 0 | `0x38` / `0xB8` | `0x00..0x1F` |
| 1 | `0x39` / `0xB9` | `0x20..0x3F` |
| 2 | `0x3A` / `0xBA` | `0x40..0x5F` |
| 3 | `0x3B` / `0xBB` | `0x60..0x7F` |
| 4 | `0x3C` / `0xBC` | `0x80..0x9F` |
| 5 | `0x3D` / `0xBD` | `0xA0..0xBF` |
| 6 | `0x3E` / `0xBE` | `0xC0..0xDF` |
| 7 | `0x3F` / `0xBF` | `0xE0..0xFF` |

### Command examples for a test fixture

| Target address | Extended read command (two bytes) | Extended write command (two bytes; then data) |
| --- | --- | --- |
| `0x00` | `B8 01` | `38 01` |
| `0x0F` | `B8 3D` | `38 3D` |
| `0x10` | `B8 41` | `38 41` |
| `0x13` | `B8 4D` | `38 4D` |
| `0x1F` | `B8 7D` | `38 7D` |
| `0x20` | `B9 01` | `39 01` |
| `0x7F` | `BB 7D` | `3B 7D` |
| `0xFF` | `BF 7D` | `3F 7D` |

**Aliasing test:** write logical `PRAM[0x00]` via legacy `0x41 <data>`, then read via extended `0xB8 0x01` and legacy `0xC1`; all accesses must refer to **one** backing byte. Likewise, legacy `0x21` and extended `0xB8 0x41` must both address logical `PRAM[0x10]`. Do not silently copy an internal-array indexing shortcut from another emulator.

## 6. Time counter byte order and the Linux epoch

The RTC seconds value is **one 32-bit unsigned counter**, split into **four individually addressable little-significance-first registers** (not BCD calendar fields and not memory-mapped big-endian 68000 words).

```text
seconds32 = b0 | (b1 << 8) | (b2 << 16) | (b3 << 24)

b0: read cmd 0x81  (least significant)
b1: read cmd 0x85
b2: read cmd 0x89
b3: read cmd 0x8D  (most significant)
```

This byte significance is independent of the 68000's big-endian memory access convention.

The seconds epoch begins at **1904-01-01 00:00:00**. The host Linux Unix epoch starts at **1970-01-01 00:00:00**, which is **2,082,844,800 seconds later**.

```c
// Illustrative arithmetic, not an API or final design approval.
int64_t classic_seconds = (int64_t)unix_seconds + INT64_C(2082844800);
uint32_t rtc_seconds = (uint32_t)classic_seconds;  // explicit 32-bit hardware wrap
```

Use a 64-bit intermediate before reduction. Current host time should initialize the virtual counter when no persistent clock adjustment exists. If the Mac writes one or more seconds bytes, the value must remain guest-owned and continue ticking; **never set the Linux host system clock**. The RTC's counter and PRAM must survive a CPU reset; PRAM and clock-offset state must survive emulator restarts when persistence is enabled.

The counter crosses its 32-bit wrap boundary in February 2040. Test the wrap, partial register writes, and reads straddling a one-second transition. The precise coherence model for byte-at-a-time reads/writes and guest time changes is an **implementation policy to specify and test** in PLUS-EMU-0009, not an invented latch feature of the IC.

## 7. Parameter RAM map: hardware vs software meaning

At the **hardware level**, all 256 PRAM bytes are simply battery-backed 8-bit storage. The RTC does not assign meanings such as speaker volume, printer settings, checksum, mouse speed, or startup disk to individual addresses. Those meanings are imposed by Macintosh ROM and System Software.

| Logical PRAM range | Hardware access |
| --- | --- |
| `0x00..0x0F` (16 bytes) | Both legacy one-byte commands `0x41..0x7D`/`0xC1..0xFD` and extended commands |
| `0x10..0x13` (4 bytes) | Both legacy one-byte commands `0x21..0x2D`/`0xA1..0xAD` and extended commands |
| `0x14..0xFF` (236 bytes) | Extended commands only |

The first 20 bytes are not stored twice. An OS-level in-RAM copy of PRAM is **not the same thing** as the battery-backed RTC storage; no direct CPU access to `PRAM[A]` exists.

For the Plus ROM specifically, the observed startup sequence reads PRAM `0x00` (command `C1`, checks for `A8`) and PRAM `0x10` (command `A1`, extracts volume); **these are examples of ROM interpretation, not IC-defined defaults**. The remaining system-specific meanings and any checksum policy should be confirmed against the guest ROM/System Software before fixture initialization.

A new virtual PRAM store should faithfully expose bytes and persist them, not pre-populate unexplained “valid Mac settings” that conceal initialization problems. See [PLUS-EMU-0009](PLUS-EMU-0009.md) for backing-file lifecycle and error-handling requirements.

## 8. Write protection and transaction state

A practical decoder needs at least the following transient states:

```text
DESELECTED
  -- PB2 low --> COMMAND (receive 8 bits MSB first)
COMMAND
  -- regular read --> SEND_DATA (8 bits)
  -- regular write --> RECEIVE_DATA (8 bits)
  -- extended prefix --> EXT_ARGUMENT (8 bits)
EXT_ARGUMENT
  -- read --> SEND_DATA (8 bits)
  -- write --> RECEIVE_DATA (8 bits)
RECEIVE_DATA / SEND_DATA
  -- complete --> COMPLETE (await deselect)
ANY SELECTED STATE
  -- PB2 high --> DESELECTED (abort/reset transient shifter)
```

Keep **nonvolatile** registers (PRAM, seconds/host offset) distinct from the **transient** bit shifter and command state. When write protection is set, reject writes other than an allowed change to the write-protection register; reads remain available. A CPU reset must not erase PRAM. Record any assumptions about simultaneous/extra clock pulses after byte completion.

**Open edge-case checks:** first read bit timing when DDRB becomes input; effect of PB1 state at select/de-select; legal low-order command bits beyond the canonical encodings; behaviour when a transfer is interrupted after 1–7 bits; exact diagnostic test-mode effects; and the degree of time-counter latching across four separate reads.

## 9. One-second interrupt

The RTC's one-second clock signal is visible in the Macintosh Plus **VIA IFR bit 0**. The vertical blanking interrupt is **IFR bit 1**. The VIA's IER bit 0 independently masks/unmasks the one-second interrupt to the MC68000; masking does not mean the RTC seconds counter stops advancing.

Important implementation distinction: the current emulator's `umac_1hz_event()` calls `via_caX_event(1)` and sets its own internal `VIA_IRQ_CA = 0x01`; those function names should **not** be mistaken for definitive hardware 6522 CA1/CA2 pin identities. Preserve guest-visible IFR/IER bit meanings and ensure a single one-second event source, without changing VBL or keyboard behaviour.

No internal 32.768 kHz oscillator-cycle simulation is needed for the intended ROM-visible fidelity; an abstract per-second counter and correctly surfaced interrupt events are sufficient unless observed ROM behaviour proves otherwise.

## 10. Emulator integration checklist

The RTC is a **device behind VIA GPIO**, not a direct CPU-decoded peripheral. Developers should inspect:

- `devel/umac/src/via.c`: Port B ORB/DDRB handling, input/output merge, change callbacks, IFR/IER, 1 Hz tick stub.
- `devel/umac/include/via.h`: existing `via_cb` interface and lack of explicit DDRB change notifications.
- `devel/umac/src/main.c`: `via_rb_changed()` is currently empty for PB0–PB2; `via_rb_in()` currently produces mouse bits only; `umac_init()`/reset/loop.
- `devel/umac/src/unix_main.c`: `gettimeofday()`, `umac_1hz_event()`, instance lifecycle and argument handling.
- `devel/umac/CMakeLists.txt`: RTC source/test integration.
- `docs/tasks/db/PLUS-EMU-0009.md`: approved-vs-proposed scope, persistence choices, tests and review gate.

Recommended separation: a platform-neutral serial RTC core with a clock provider, a Linux persistence/time adapter, and a narrowly extended VIA Port B callback. Do not read the host clock for each individual serial bit or patch ROM/system memory to answer time queries.

## 11. Minimal independent verification vectors

These are **reference vectors**, not claims of tests already run:

1. One-byte reads `81 85 89 8D` reconstruct one 32-bit seconds counter; `91 95 99 9D` select mirrored seconds registers.
2. With host Unix seconds set to `0` and zero guest offset, the RTC should report `0x7C25B080` (1904-to-1970 offset) **if** the virtual clock is sampled at that exact reference instant; verify by independent arithmetic before accepting as a fixture.
3. Legacy `C1` accesses PRAM `00`, **not** time; legacy `A1` accesses PRAM `10`, **not** time.
4. Extended addresses `00`, `13`, `1F`, `20`, `FF` use the command pairs in section 5; different addresses remain independent.
5. Legacy and extended reads of `PRAM[00]` and `PRAM[10]` return identical bytes after writes by either interface.
6. Assert protection with `35 80`, verify ordinary and extended writes cannot change PRAM or seconds; clear with `35 00`, repeat.
7. Abort with PB2 high halfway through a command: the partial data must not become a completed write.
8. Toggle DDRB bit 0 without writing ORB: the next PB0 read must use the device-driven bit, not the previous output latch.
9. Confirm one-second IFR/IER bit 0 operation with VBL bit 1 unaffected.
10. Restart/reload: all 256 PRAM bytes persist and guest-set time still advances; normal CPU reset is not a factory reset.
