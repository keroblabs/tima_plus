# Micro Mac (umac)

This Macintosh Plus emulator builds on MicroMac v0.22 and the Musashi MC68000
interpreter. The desktop build uses the original Mac Plus V3 ROM, a 512 × 342
monochrome display, 4 MiB of RAM by default, and an internal 800K floppy.
It also emulates the VIA timers and keyboard interface, SCC mouse input,
RTC/PRAM, and the NCR 5380 SCSI controller with one optional hard disk.

An embedding application owns the RAM, original ROM and internal drive.
Create the drive with `disk_img_open(path)` or pass a null path for an empty
installed drive. `disk_img_open_writable(path)` enables writes. If
`disk_img_close()` returns `-1`, the caller still owns the drive and can retry
saving its dirty tracks. Each `umac_loop()` advances about 5 ms of emulated time.
Use `umac_ticks()` for the virtual C8M clock, `MAC_FRAME_TICKS` for vertical
blanking, and the RTC's time source to schedule the one-second VIA event.

```c
umac_init(ram, rom, internal_floppy);
umac_loop();
/* Deliver these when due. */
umac_vsync_event();
umac_1hz_event();
/* Deliver input transitions as they occur. */
umac_kbd_event(mac_scancode, down);
umac_mouse(delta_x, delta_y, button_state);
/* Read the framebuffer at ram + umac_get_fb_offset(). */
```

# Prerequisites

To build on Linux, you'll need `SDL2` installed (packaged as
`libsdl2-dev` on Ubuntu).

The desktop build uses the sibling [Musashi checkout](../Musashi) at
`../Musashi` instead of the original `external/Musashi` submodule.

Supply a 128 KiB unmodified Macintosh Plus V3 ROM with checksum `4d1f8172`.
For floppy boot, attach a bootable raw Macintosh 800K image (819,200 bytes)
or a Macintosh 800K DiskCopy 4.2 image (838,484 bytes with sector tags).
DiskCopy images are validated and their 12-byte sector tags are preserved.
Raw images and tagless DiskCopy images use zero-filled tags. System 6.0.8
System Tools is a verified boot image.

# Build

## CMake

If you opened `devel` in VS Code, run **CMake: Configure** and
**CMake: Build**. The workspace settings use `umac` as the source
directory and put the build in `umac/build-cmake`.
In **Project Outline**, expand the `umac` project to find the `umac`
emulator target.

To build from a shell, run these commands from the `umac` directory
with CMake 3.16 or later:

```sh
cmake -S . -B build-cmake
cmake --build build-cmake --parallel
```

The executable is `build-cmake/umac`. [CMakeLists.txt](CMakeLists.txt)
lists the sources, include directories, and build flags explicitly.
The Musashi opcode files are generated in the build directory, not in
the sibling checkout.

Set `-DMEMSIZE=<size_in_KiB>` at configure time to choose the amount of RAM.
The guest display uses the Mac Plus ROM's native 512 × 342 resolution.

## Make

```sh
make
```

Set `DEBUG=1` for instruction tracing or `MEMSIZE=<size_in_KiB>` to choose the RAM size.

This builds the SDL2 executable `main`.  `make prepare` generates
`m68kops.c` and `m68kops.h` from templates in the sibling Musashi
checkout, and runs automatically as needed by `make`.  The desktop
build uses [umac's Musashi configuration](include/m68kconf.h) and keeps
its Musashi object files in `build/musashi`, separate from objects built
by Musashi's own Makefile.

For an RP2040 Pico build, `tools/decorate_ops.py` can mark hot opcode
handlers with `M68K_FAST_FUNC` to place them in RAM instead of flash.
The desktop build does not modify the generated opcodes this way.

Some low-quality (so uncommitted) and undocumented profiling code was
used to generate the `tools/fn_hot200.txt` list of the 200 most
frequently-used 68K opcodes.  This was generated by profiling a System
3.2 boot, using MacWrite and Missile Command for a bit.  :D Out of
1967 opcodes, these hottest 200 opcodes represent 98% of the dynamic
execution.  (See _RISC_.)

# Running

From the `umac` directory, run the CMake-built executable:

```
./build-cmake/umac -r rom.bin -d System608.image
```

If you built with the Makefile, use `./main` instead.

The SDL frontend runs the CPU as fast as the host allows. Floppy and VIA
timer operations use the emulated C8M clock. Screen presentation, guest
vertical blanking and the guest one-second clock interrupt use wall time
to keep the display and input timing usable at desktop speeds.

The host pointer is free at startup. Left-click the emulator window to
capture it; that click is not sent to the Mac if capture succeeds.
Press **F12** or switch away from the window to release it.

The RAM is actually a memory-mapped file, which can be useful for
(basic) debugging: as the emulator runs, you can access the file and
see the current state.  For example, you can capture screenshots from
screen memory (see `tools/mem2scr.c`).

For standalone firmware tests, use `--raw-rom -r /path/to/test.rom`.
This option accepts a regular 128 KiB raw MC68000 reset image and skips
the Plus V3 checksum. The build configuration selects the hardware map.
Run from a separate working directory because uMac truncates `ram.bin`
on launch. See [Tima ROM](../tima_rom/) for a standalone ROM experiment.

### Development-only MC68681 debug peripheral

Development builds map the MC68681 at `0xC00000–0xC0001F`. Its sixteen
8-bit registers use the MC68000's lower byte lane (odd addresses).
UART-B transmit-ready is at `0xC00013` and transmit data is at
`0xC00017`. The SDL frontend forwards UART-B bytes to stdout with either
an alternate reset ROM or the original Plus V3 ROM and an 800K floppy.
Embedders can attach a stream with `umac_debug_uart()` after `umac_init()`.

The build option `UMAC_DEVELOPMENT_DUART` defaults to CMake `ON` and
Make `1`. For the production M0001AP map, configure CMake with
`-DUMAC_DEVELOPMENT_DUART=OFF` or run `make UMAC_DEVELOPMENT_DUART=0`.
Both settings compile out the device and its address decode. Confine
guest use of the debug console to development code or provide a fallback
for physical firmware.

To run the disk UART regression, configure the development build with
`-DUMAC_TEST_PLUS_ROM=/path/to/rom.bin` and
`-DUMAC_TEST_VASM=/path/to/vasmm68k_std`. The `m68681_plus_rom_disk`
CTest assembles its own 800K boot floppy and checks the live UART-B
output. The production build runs `m68681_production_map` to verify the
unmapped window. See [PLUS-ROM-0002](../../docs/tasks/db/PLUS-ROM-0002.md)
for the test evidence.

For a `DEBUG` build, add `-i` to get a disassembly trace of execution.

Use `-W loaded.rom` to dump the loaded ROM bytes for comparison with the
input file. `--trace-iwm` reports ROM PCs, virtual ticks, drive-control signals,
IWM status, and write and checkpoint outcomes.

### Writable floppies

Use `-d disk.image -w` to enable persistent floppy writes. `-d` alone mounts
the floppy write protected. `-p` enables SCSI writes independently.

Tagged DiskCopy 4.2 images preserve both the 512-byte data and the 12-byte tag
of every sector. Raw `.dsk` images save the 512-byte sector data even when the
guest write carries nonzero tags. Those tags are available while the encoded
track is cached. Rebuilding it from the raw file supplies zero tags. Tagless
DiskCopy images accept data-only saves and reject a checkpoint that would
lose nonzero tags.

The emulator saves dirty tracks when moving to another cylinder, ejecting, or
closing the window. A failed save blocks the move, eject or close and reports
the error. The `.iwm.lock` sidecar coordinates writable sessions across atomic
replacements of the image file.

### Floppy tests

The native IWM tests use generated images. They cover drive signals, read and
write timing, GCR encoding and decoding, format rollback, media protection,
and checkpoint failure and retry.

To test original System Software boot, configure with your unmodified
Mac Plus V3 ROM and a bootable raw or DiskCopy 4.2 800K floppy.

```sh
cmake -S . -B build-cmake \
  -DUMAC_TEST_PLUS_ROM=/path/to/rom.bin \
  -DUMAC_TEST_PLUS_FLOPPY=/path/to/System608.image
cmake --build build-cmake --parallel
ctest --test-dir build-cmake --output-on-failure
```

The ROM test checks Finder, display and keyboard/mouse input. The original
`.Sony` driver reads sectors and tags on both heads and in all five speed
zones, reports a write-protection error, and recalibrates during a reboot from
cylinder 79. With 4 MiB of guest RAM and Python 3, the SDL boot test also checks
startup time and the guest clock and VBL rates.
To collect the MMIO trace, run `build-cmake/umac_iwm_rom_test ROM FLOPPY --trace`.

`iwm_plus_rom_write` and `iwm_plus_rom_format` use disposable copies. They
exercise `.Sony` writes, immediate read-back, seek-triggered persistence,
format gap retry, full-disk verify and reopening. Raw and tagged media boot
with writes enabled. On Linux, the tagless DiskCopy tests simulate write
protection during startup, then exercise the writable drive with `.Sony`.

## SCSI hard disks

Without `-d`, the floppy drive is installed and empty. SCSI works with or without a floppy.
Attach a raw, whole-device image read-only with `-s`:

```sh
./build-cmake/umac -r rom.bin -d System608.dsk -s HD10_512.hda
```

The default is ID 1, LUN 0. Use `-t 0` through `-t 6` to override the
target ID (the Mac is ID 7). The filename is not interpreted. Add `-p`
to enable in-place writes; **use a copy of the image**. A successful
WRITE(6) or WRITE(10) syncs the file before returning GOOD. This does not roll back
sectors already written if a multiblock command is interrupted or fails.
Do not modify the backing file from another process while it is mounted.

Use a regular image file containing 1 to 2,097,152 512-byte sectors
(up to 1 GiB). Block 0 is the first 512 bytes, with no emulator header
or conversion. The Macintosh Plus ROM expects a driver descriptor at
device block 0, a Plus-compatible disk driver and an Apple Partition Map.
An HFS-only volume image, even with an `.hda` extension, will not mount
by itself. Convert it before attaching it. Booting also requires a
bootable System volume.

### Convert an HFS volume

Use [hfs_to_device.py](tools/hfs_to_device.py) with Python 3.10+ and a
whole-device template that already has a Macintosh Plus-compatible
disk driver (for example, Apple Driver 4.3). Run from the `umac`
directory:

```sh
python3 tools/hfs_to_device.py kiosky.hda \
    --template 320_32MB_drive.hda --output HD10_512.hda
./build-cmake/umac -s HD10_512.hda
```

The script copies the template's partition map and driver and replaces
its final HFS partition with the input volume byte-for-byte. The input
must be a raw classic HFS volume that fits that partition; Disk Copy
headers, HFS+, and multiple-volume templates are not supported. No
driver or System software is bundled. The script does not change either
input, overwrite existing output, or install or bless a System Folder.
Add `-d System608.dsk` if you want to boot the floppy and mount the
converted disk as a second volume.
For other layouts, see [Disk Jockey](https://diskjockey.onegeekarmy.eu/).

The standalone converter tests use generated fixtures:

```sh
python3 -m unittest discover -s tests -p test_hfs_to_device.py
```

### SCSI controller behavior

Supported commands are TEST UNIT READY, REQUEST SENSE, INQUIRY,
READ(6)/WRITE(6), READ(10)/WRITE(10) and MODE SENSE(6) for the current
header/block descriptor (including the write-protect bit). Other commands
return CHECK CONDITION.
The controller supports polled REQ/ACK and CPU-driven pseudo-DMA. The
Macintosh bus timing model applies when the CPU accesses its registers. It has no target mode, contention,
disconnect/reselect, MESSAGE OUT, parity faults or external DMA/EOP.
Byte reads use even addresses; writes use odd addresses. An aligned
word accesses only the applicable lane (upper read, lower write); an
aligned long is two successive word cycles. These wider-access rules
are emulator conventions not yet verified on physical hardware.

### SCSI tests

With the CMake test target `umac_scsi_test` built (enabled by default),
run the two headless cases from `umac`. They use synthetic data only:

```sh
./build-cmake/umac_scsi_test controller
./build-cmake/umac_scsi_test disk
```

The controller case covers address decoding, register state, arbitration,
selection and valid/invalid handshakes. The disk case reads LBA 100,
writes sectors with PIO and pseudo-DMA, closes and reopens its
disposable image, then checks the exact raw bytes, neighboring
sectors and SCSI error reporting.

If you have a Mac Plus V3 ROM, `umac_scsi_test rom /path/to/rom.bin`
also exercises a persistent sector round trip using the *unmodified
SCSI Manager routines* under Musashi. Give CMake the
`UMAC_TEST_PLUS_ROM` file path to include this case in test discovery.
This tests the firmware I/O routines in isolation, not booting/mounting
a partitioned image or using physical BlueSCSI hardware.

# Hacks/Technical details

If you're writing an emulator for an olden Mac, some
pitfalls/observations:

  * The ROM overlay at reset changes the memory map, and the address
    decoding for read/write functions has to consider this.  Overlay
    is on for only a handful of instructions setting up RAM exception
    vector tables so, for performance to avoid checking on every
    access, there should be two versions of memory read/write
    functions that are selected when the overlay changes.  This has
    been implemented only for instruction/opcode fetch.

  * The IWM receives Macintosh GCR bit cells from a circular track
    generated by the disk backend. The backend is a logical 800K drive with
    a variable-speed spindle and two heads. VIA PA5 selects Sony drive
    registers and VIA Timers 1 and 2 support the ROM's drive delays and
    tachometer polling. See [the IWM architecture](../../docs/04-iwm-emulation.md).

  * The OS's keyboard ISR is easy to confuse by sending bytes too fast,
    because a fast response's IRQ will race with the ISR exit path and
    get lost.  The `main.c` keyboard emulation paces replies
    (`kbd_check_work()`, `kbd_rx()`) so as to happen a short time
    after the Mac sends an inquiry request.

  * Mouse: The 8530 SCC is super-complicated.  It's easy to think of
    the 1980s as a time of simple hardware, but that really applies
    only to CPUs: to compensate, the peripheral hardware was often
    complex, and SCC has a lot of offloads for packetisation/framing
    of serial streams.  It is this chip that enables AppleTalk,
    relatively high-speed packet networking over RS422 serial cables.
    Two spare pins (for port A/B DCD detect) are used by the mouse;
    the Mac 128K is a nose-to-tail design, no part of the animal is
    wasted.  Uh, anyway, only enough of the SCC is supported to make
    the mouse work: IRQ system for DCD-change, driven from one half of
    a quadrature pair on X/Y.  The ISR for those lines then samples
    the VIA PORTB pins for the corresponding other half of the pair.
    Finally, the emulator interface takes a movement delta dx:dy for
    convenience; a quadrature step is performed for each unit over a
    period of time.

  * I didn't use the original Mac128 ROM.  First, Steve Chamberlin has
    done a very useful disassembly of the MacPlus ROM (handy to
    debug!) and secondly I misguidedly thought that more stuff in ROM
    meant more RAM free.  No, the 128K MacPlus ROM uses more RAM (for
    extra goodies?) than the original 64K Mac 128K ROM.  It does,
    however, have some bug fixes.  Anyway: the MacPlus ROM runs on
    512K and 128K Macs, and was used as the 'e' in the Mac 512Ke.
